# Extraction benchmark for CBC tables

Three arms over one corpus of 814 images and 8,140 hand- and generator-labelled fields. The **pattern layer** runs the production regex set over the exact text the generator drew, with no glyph reading in the loop, and is therefore a *ceiling*: recall 0.997 at precision 1.000. The **Tesseract arm** runs the real production path on the rendered images: recall 0.540 at precision 0.987. A third arm repeats the OCR path with the page-segmentation mode the code shipped with, which is reported because it was wrong -- see M4.

Both arms share the patterns, the alias table, the canonicalisation and the ground truth. **The only difference between them is where the text came from**, so the difference in recall is glyph reading and nothing else. With the ceiling at 0.997, essentially the whole remaining loss is attributable to OCR. §4 does that subtraction per stratum and per parameter.

**Headline finding: glyph errors reintroduce silent wrong values.** M1 and M2 eliminated them at the pattern layer, which now emits none. Real OCR produces **38**, of which **13 grade a cytopenia less severe than it is**. A misread digit is not caught by the unit boundary, because the unit is read correctly and the number is simply wrong and plausible. See §4.

The GPT-4o-mini vision arm remains deferred by decision; its adapter is complete in `backends.py` and hard-guarded against making a network call.

`extractable` means the page prints both a value and a unit, so a correct quantity is obtainable. `no_unit` means the value is printed and the unit is not -- **refusing is the correct outcome** and any number emitted is a guess. `absent` means the analyte is not on the page at all, so silence is correct. ### Fields and judgements are different counts

**A wrong quantity scores as both a false positive and a false negative** -- the backend claimed something untrue *and* failed to produce the truth. So a field with a wrong value contributes two confusion-matrix entries, and `TP + FP + FN + TN` exceeds the number of fields by exactly the number of wrong-value fields.

Every table below carries a `Fields` column beside its TP/FP/FN/TN so the two reconcile on sight rather than looking like an arithmetic error.

In this pass the two coincide at **1390**, because no field carries a wrong value -- every failure was a refusal, which contributes one judgement, not two. Earlier runs did diverge: as found, stratum B scored 1,080 fields as 1,112 judgements, the excess being its 32 wrong-value fields. See §the fixes section.

Read that table before the one above it. JPEG compression is survivable all the way down to quality 20 -- a setting that visibly wrecks the image to a human eye -- while half a pixel of extra Gaussian blur past sigma 0.5 takes everything. A pipeline tuned on the assumption that image quality degrades gracefully would be tuned on the wrong axis.

Two anomalies worth naming rather than smoothing over. **Blur at sigma 0.5 scores *above* the pristine control**, which is not noise: a half-pixel blur anti-aliases the micro sign's thin strokes and makes it more legible, not less -- the same resolution story as the upscaling probe in the gap section. And the **left-lit shadow is fatal while the diagonal and corner ones are not**, because the left of the page is where the row labels are: darken those and no pattern matches a label, so the row is never sighted at all.

### Do glyph errors reintroduce silent wrong values?

**Yes. 38 of them, 13 understating a CTCAE grade.**

This is the finding, not a footnote. M1 and M2 removed every silent error at the pattern layer by making the *parse* refuse what it could not resolve. A misread digit defeats that, because nothing about it is unresolvable: the unit is read correctly, the separators are unambiguous, the number is simply wrong. It then has to clear only the `cbc.ANALYTES` plausibility bounds, which are deliberately wide enough to admit real pathology -- a platelet count of 9,000 and one of 90,000 are both perfectly possible, so nothing downstream can tell that a digit moved.

The unit boundary was never designed to catch this and cannot. It guarantees that a value arrives with a known scale, not that the digits are the ones on the page. Catching these needs either a second read to agree with the first, or a confidence-gated refusal, or an operator confirming the figures against the image -- none of which this pipeline has.

### The gap had one dominant cause: the micro sign

The per-parameter table used to split cleanly in two, and the split was not about the analytes. It was about their units.

Tesseract reads `µ` as `p`. Straight from the OCR text of a pristine render at confidence 91:

```
Absolute Neutrophil Count (ANC) 3,900 cells/pL 1,500 - 8,000
                                      ^^^^^^^^ the page prints cells/µL
```

`cells/pL` did not match `_U_COUNT`, so the unit was dropped and the field refused. Every count analyte prints a microlitre denominator and no other analyte does, which was the whole of the pattern: the counts scored 0.221-0.305 recall against 0.670-0.779 for everything else.

#### The fix, and what it moved

`pL` is now accepted in the microlitre denominator and rewritten to `uL` at the OCR boundary. It is **not** registered in `units.py`: a picolitre is a real unit, `cells/pL` is a misreading rather than a spelling, and a corruption admitted to the alias table would then be accepted from the keyboard and from the REST API too, where there is no OCR to blame. The rewrite is also scoped to a denominator following a slash, because a blanket `p`-for-`u` would turn picograms into micrograms and corrupt every MCH on every report.

Accepting it costs no ambiguity: a picolitre is a millionth of a microlitre, so no laboratory reports a cell count per picolitre and there is nothing for `cells/pL` to be confused with.

Measured over the full 814 images, before and against after:

|  | Before | After |
|---|---|---|
| Stratum A | 1.000 / 0.172 | 1.000 / 0.172 |
| Stratum B | 0.994 / 0.689 | 0.995 / **0.767** |
| Stratum C | 0.987 / 0.460 | 0.985 / **0.506** |
| Pooled | 0.988 / 0.489 | 0.987 / **0.540** |
| Count-analyte recall | 0.228 | **0.353** |
|   of which ANC | 0.101 | **0.287** |
| `unit_dropped` losses | 877 | 695 |
| Silent wrong values | 31 | **38** |
|   of which understate severity | 9 | **13** |

Precision / recall. **268 fields recovered**, and ANC -- which the micro sign had hit hardest -- nearly tripled.

**And silent wrong values went up, from 31 to 38.** That is not a side effect to bury: recovering a field means letting it through, and some of what comes through is wrong. The fields this fix recovers were previously refused for a *unit* problem, which was masking a *digit* problem underneath. Raising recall on a pipeline with no digit check necessarily raises the count of plausible wrong answers, and that trade has to be stated rather than netted off against the recall gain.

#### Against the upscaling lever

Both levers address the same glyph, so the question is whether they add. Measured on the same stratified 40-image sample, end to end:

|  | Recall | Count-analyte recall | Silent |
|---|---|---|---|
| 1x, no `pL` rule | 0.587 | 0.266 | 3 |
| **1x + `pL` rule** | **0.674** | **0.481** | 3 |
| 2x, no `pL` rule | 0.697 | 0.571 | 1 |
| 2x + `pL` rule | 0.697 | 0.571 | 1 |

**They are substitutes, not complements.** 2x with the rule is identical to 2x without it, because upscaling already cuts the `/pL` misreads from 53 to 7 and leaves the rule almost nothing to do. Applying both buys nothing over applying either.

The pattern-layer rule captures most of the benefit -- count-analyte recall 0.266 to 0.481 against upscaling's 0.571 -- for no image processing, no runtime cost, and no proximity to the 3x cliff, where recall collapses to 0.084 and silent errors jump to 52. Upscaling still edges ahead on both recall and silent errors, so the rule is **not strictly better**; it is cheaper and safer for most of the gain. Taking the remaining ~0.09 of count-analyte recall means accepting a preprocessing parameter with a cliff one step past the optimum, which is a judgement about operational risk rather than a measurement.

Neither lever is finished business. The next most common corruption in the same sample is `µ` read as `y` -- 24 occurrences of `/yL` at 1x, against 53 of `/pL`. It is not handled, deliberately: the `p` rule was scoped to one glyph so its effect could be attributed, and adding a second in the same change would have made both unmeasurable.

## 5. The four defects it found

Each was confirmed directly against the production module rather than inferred from the aggregate. Three are fixed and one is open. M4 was found only when Tesseract was installed, and would have made every OCR number in this report meaningless.

### M1. The value parse had no decimal-mark policy - **fixed**

`_NUMBER` was `(?P<value>\d[\d,]*\.?\d*)`, finished with `float(text.replace(",", ""))`: commas stripped, points honoured. That is the US convention hard-coded, so `6.500` read as 6.5 and `0,9` read as 9.

As found (recorded), recall across the two decimal styles was 0.867 for a point against 0.233 for a comma, and precision 1.000 against 0.724. **32 wrong quantities reached the panel and 16 of them graded a cytopenia less severe than it is** - a WBC printed `0,8`, meaning 800 cells/uL and CTCAE grade 4 leukopenia, read as 8,000 and graded 0. Finding 4's signature by a different mechanism: not magnitude inference, a separator strip, and pointing the same way.

**The fix rests on one fact: a thousands separator is always followed by exactly three digits.** So the shape of the token settles most cases with no context at all:

| Token shape | Reading | Example |
|---|---|---|
| no separator | integer | `6500` -> 6500 |
| separator + 1, 2 or 4+ digits | **decimal mark**, unambiguously | `0,9` -> 0.9; `4,80` -> 4.80 |
| two different separators | last is the decimal mark | `1.234,56` -> 1234.56 |
| one separator repeated | all grouping - a number has one decimal mark | `1.234.567` -> 1234567 |
| separator + exactly 3 digits | genuinely ambiguous | `6,500`, `250.000` |

That alone resolves all four understating cases deterministically - `0,9`, `0,8`, `0,2` and `2,0` each have one digit after the separator - and turns `6,500` and `3.900` into refusals.

A **document-level second pass** then recovers those. A page that prints `13.0` or `83.5` anywhere has shown that `.` is its decimal mark, and therefore that `,` groups its thousands throughout. The evidence comes from the document, not from a convention we picked. Contradictory evidence on one page yields no inference rather than a majority vote, and its ambiguous tokens are refused.

Where nothing settles it, the number is refused with the printed token attached - `AmbiguousNumberError`, the same stance this codebase already takes on a missing unit. On this corpus that path never fires (0 fields): every generated page carries at least one unambiguous decimal, because RBC is always printed to two places. It is exercised directly in `tests/test_number_parsing.py`.

After the fix, recall by decimal style is 1.000 for a point over 540 fields and 1.000 for a comma over 540.

### M2. The SI unit alternation could not match any SI unit - **fixed**

`_U_COUNT` built its SI alternative as `r'10\^?[369]\s*/\s*[l{0}]+'.format(_MU)` with `_MU = r'[u\u00b5\u03bc]'`. Interpolating a character class inside another gives `[l[uµμ]]+`, which Python parses as the class `[l[uµμ]` followed by a **required literal `]`**. So `10^9/L]` matched and `10^9/L` did not.

Two further defects sat in the same expression. `[369]` is a single digit, so `10^12/L` - the SI unit for a red cell count - could not have matched even with the brackets fixed. And `10\^?` made the caret optional, so `109/L` matched and was read as an SI unit.

As found (recorded), SI recall was 0.450 against 0.617 for cells/uL and 0.583 for K/uL, and the loss was entirely in the pattern layer - `units.parse_unit` had accepted `10^9/L` and `10^12/L` all along.

The fix splits the micro characters into a bare list so no class is nested, allows `(?:12|0|3|6|9)` as the exponent, and **requires** an exponent marker - a caret, `e`, `*`, or a run of superscript digits, which are self-marking and need none. One case is deliberately given up: OCR that flattens a superscript to a plain digit turns `10⁹/L` into `109/L`, which is now a refusal. That is the right way round - `109` is a perfectly possible printed value, so the old match was never safe, and a refusal is recoverable where a wrong scale is not.

After the fix, recall by scale is 1.000 for SI, 1.000 for cells/uL and 1.000 for K/uL.

### M3. Three gaps stack on one real image - **open**

`test_4.png` (A4) prints its rows as `RBC Count`, `WBC Count` and `Platelet Count`, with units spelled `million cells/mcL`, `cells/mcL` and `/mcL`. Three of its four fields are lost, and the pattern layer loses them at the **first** of three independent gaps:

1. `_ANALYTE_LABELS` has no `"<abbrev> Count"` form, so those three rows match no pattern at all and the analyte is never sighted. Attributed to `no_read`, correctly, and not to the alias table.
2. Given a label the patterns know, the rows match but return `unit: None` - `mcL` is absent from `_U_COUNT` too.
3. The alias table now accepts `cells/mcL`, so this third gap is closed. The first two are not.

These three fields are **the only remaining losses in the whole pass** - 3 false negatives out of 929 extractable fields. Fixing gap 1 alone would turn them into refusals rather than values, because gap 2 still stands, which is why they are quoted together.

### M4. The page-segmentation mode read almost nothing off a table - **fixed**

Found the moment Tesseract was installed, and it would have made every OCR number in this report meaningless. Both OCR call sites passed `--oem 3 --psm 6`. **psm 6 means "assume a single uniform block of text"**, and a bordered table with columns is not that: Tesseract runs the rows together across the grid lines and returns rubbish. On a pristine, high-contrast generated report at OCR confidence 90 it returned the two title lines perfectly and, for the entire ten-row table, `Cr ee` / `rucr ||| ars`.

Preprocessing was not the cause and was ruled out before the mode was: denoising, Otsu thresholding and 2x upscaling each change the result by nothing at all under psm 6, and every other mode reads 8/8 values with or without them.

The replacement was chosen by measurement over a stratified sample of 24 images spanning the clean control and the worst level of every degradation family, scored end to end through the real pipeline:

| psm | Meaning | Precision | Recall |
|---|---|---|---|
| **3** | fully automatic (**chosen**) | 0.987 | 0.419 |
| 4 | single column, variable sizes | 0.974 | 0.425 |
| 11 | sparse text | 1.000 | 0.229 |
| 12 | sparse text with OSD | 0.977 | 0.235 |
| 6 | single uniform block (**as shipped**) | 1.000 | 0.022 |

psm 3 over psm 4 on precision and on silent errors, which is the trade this application makes everywhere else. Note that the sparse-text modes read *more* characters and score worse: they do not preserve reading order, and the patterns need a row's label, value and unit on one line. Glyph accuracy is not the objective; field recovery is.

Worth recording how close this came to being invisible. The arm would have run, produced a number, and that number would have been attributed to glyph reading - which is exactly the inference this report was asked to make. A one-line configuration default would have been reported as the difficulty of reading laboratory reports.

## 6. Alias coverage

A direct sweep of 48 unit spellings against `units.parse_unit`, no images involved. A corpus can only exercise the spellings it was told to draw, and laboratories print many more than are worth rendering.

**43 accepted, 2 need an alias, 3 are not expressible at all.**

| Printed spelling | Denotes | parse_unit gives | Status | Note |
|---|---|---|---|---|
| `G/L` | thousand/uL | g/L | needs_alias | giga-per-litre, used in parts of Europe |
| `T/L` | million/uL | rejected | needs_alias | tera-per-litre, same convention |
| `L/L` | - | rejected | needs_dimension | SI haematocrit as a fraction; needs a dimensionless dimension |
| `mmol/L` | - | rejected | needs_dimension | SI haemoglobin in NL/DK/SE; needs a molar mass |
| `ratio` | - | rejected | needs_dimension | same |

`needs_dimension` is kept separate from `needs_alias` deliberately. Haemoglobin in mmol/L needs a molar mass -- the g/dL factor of 0.6206 is specific to the haemoglobin tetramer and is not a unit conversion -- and a haematocrit in L/L needs a dimensionless dimension that `units.Dimension` does not have. Registering either against a plausible-looking factor would be exactly the quiet fabrication that module exists to prevent.

### One spelling resolves to the wrong unit

- `G/L` denotes **thousand/uL** and `parse_unit` returns **g/L**. `units._normalise` lower-cases before lookup, so the giga-per-litre count spelling collapses onto the grams-per-litre mass spelling.

This currently fails safe rather than producing a wrong number: the dimension check in `Quantity.to` rejects a mass concentration handed to a count analyte, so a WBC printed `7.2 G/L` is refused with `IncompatibleUnitsError`. The consequence is a lost field and a misleading error message, not a silent error -- but it is lost for a reason the message does not name.

## 7. The fixes, and what each moved

Three runs, against the identical corpus and the identical ground truth. Only the production code changed between them, which is what makes the differences attributable.

|  | 1. As found | 2. After the alias fix | 3. After M1 + M2 (live) |
|---|---|---|---|
| Precision | 0.948 | 0.948 | **1.000** |
| Recall | 0.622 | 0.622 | **0.997** |
| True positives | 578 | 578 | **926** |
| False positives | 32 | 32 | **0** |
| False negatives | 351 | 351 | **3** |
| True negatives | 461 | 461 | 461 |
| Silent wrong values | 32 | 32 | **0** |
| of which understate CTCAE severity | 16 | 16 | **0** |
| Alias spellings accepted (of 48) | 28 | 43 | 43 |

### The alias fix moved nothing, and that is the result

`units.py` was extended first - mcL collapsed to uL, superscript, E-notation and two-digit exponents normalised, a trailing result flag stripped from a units cell. Fifteen more spellings parsed, and **not one extraction field changed outcome**. Zero. `alias_gap` was charged zero times before and zero times after.

The reason is M3 generalised: a field only reaches `units.parse_unit` if a pattern matched its label *and* captured a unit string, so every field the alias gaps would have touched was already lost upstream. The alias table was never the binding constraint.

This is the case for spending the effort on stage attribution rather than on a headline number. A recall of 0.622 with a list of unrecognised unit spellings beside it reads as a units problem, and the obvious fix is the wrong one. The fix was still right to make - the gaps are real and they are on the checked-in images - but it recovers nothing alone, and shipping it as an extraction improvement would have been a claim the measurement does not support.

### M1 and M2 moved everything that was left

Fixing the value parse and the SI alternation took recall from 0.622 to 0.997 and eliminated every silent error: 32 wrong quantities reaching the panel became 0, and the 16 that understated a CTCAE grade became 0. False positives went from 32 to 0.

Both fixes are refusal-preserving: neither invents a reading. M1 resolves what the token shape or the page settles and refuses the rest; M2 requires an explicit exponent marker and so refuses a flattened superscript rather than guessing at its scale. The remaining 3 false negatives are M3's three label-gap fields on `test_4.png`.

**What this does and does not say.** It says the pattern layer and the unit layer now read this corpus's notation correctly given perfect text. It says nothing about OCR, which has not run. The ceiling moved; whether the floor follows is what the Tesseract arm is for.

### Two spellings left unregistered deliberately

`G/L` and `T/L`, the European giga- and tera-per-litre count units. `_normalise` lower-cases before lookup, so `G/L` collapses onto `g/L` and resolves to a mass concentration. Separating them requires making the normaliser case-sensitive for one pair of units, and a wrongly case-folded haemoglobin and a wrongly case-folded white-cell count are different kinds of harm. That is a safety judgement with an argument on both sides and not one to settle inside a benchmark. Today the dimension check in `Quantity.to` refuses `G/L` for a count analyte, so it fails safe - at the cost of an error message that names the wrong reason.
